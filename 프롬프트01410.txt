# 임무: `findyoumed/bbs` (01410 PC통신 에뮬레이터) 심층 버그 헌팅 계속

## 배경
`findyoumed/bbs` 저장소, 브랜치 `claude/12-number-question-41oc5b` (main에도 이미 병합됨)에서
"댓글/답글, PDS 업로드/다운로드, 회원정보수정, 채팅" 4개 영역을 순환하며 이상한 점을 찾아
수정하는 작업을 여러 라운드 진행했다. 최근 라운드들은 특히 **DB 스키마/FK/ID 혼동 관점**(예:
게시판별로 독립 채번되는 local_id를 전역 PK 자리에 잘못 쓰는 것, 앱 자체 텍스트 userId를
Supabase Auth UUID 자리에 잘못 쓰는 것 등)에서 실제로 크고 작은 버그를 다수 발견했다. 이
문서는 그 작업을 이어받아 계속하기 위한 지시문이다.

## 지금까지 찾아 고친 것 (git log 참고, 중복 조사 방지용)
아래는 이미 커밋되어 main에 병합된 것들이다 — 재조사하지 말 것:
- 게시글 보기 데스크톱 마우스휠 스크롤 오작동 / 삭제확인(Y/N) 클릭 불가
- 한글 닉네임이 API 헤더에 실려 fetch() 전체가 깨지던 크래시
- 문의하기 화면 이탈 시 앱 전체 영구 고장 / 글쓰기 저장 실패 시 에디터 파괴 / 글수정 취소 시 엉뚱한 화면 이동
- 게시글 제목 60자 조용한 절삭(직접입력+답글자동채움 2건)
- 대화방 개설 실패 시 초안 증발 / 대화방 제목 검증(100자)과 저장상한(60자) 불일치
- **PDS 파일 업로드 기능 자체가 클라이언트에 없던 것**(서버 API는 있었음) → 신규 구현
- **첨부파일이 게시판별 local_id를 전역 posts.id로 착각해 저장** → 무관한 글 삭제 시 CASCADE로
  같이 사라지는 구조적 결함 (attachments.post_id FK 문제)
- 삭제된 글이 자리표시자(tombstone)로 바뀌어도 첨부파일은 계속 다운로드되던 모순
- 회원 nick_name/email에 DB 유니크 제약이 없어 스모크테스트가 남긴 중복 회원 465명 발견·정리,
  유니크 인덱스 마이그레이션 작성(`supabase/migrations/0021_*.sql` — **아직 실제 DB엔 미적용**,
  이 세션 네트워크 정책상 Postgres 직접 접속 불가했음. psql/pg 라이브러리로 재시도 가능하면 적용 검토)
- 채팅: `chat_room_members.user_id`/`chat_rooms.creator_id`가 앱 텍스트 userId를 써서 항상
  비어있던 문제(진짜는 context.authUserId를 써야 함) — 코드 전체 grep으로 같은 패턴 재확인 완료
- **ID검색(LI)이 실제로는 항상 닉네임으로만 비교**되던 버그(스키마 능력탐지 우선순위 오류)
- **주제어검색(K)이 화면엔 검색된 것처럼 보이면서 실제로는 3단계 모두에서 값이 유실**되어
  완전 무동작이던 버그(가장 크고 눈치채기 어려웠던 사례)
- LS/LD/KW가 `pageSize=9999` 한방 요청에 의존해 대형 게시판에서 조용히 잘릴 수 있던 잠재 결함
  → 페이지 단위 순회로 교체

자세한 내용은 `WORK_LOG.md` 최상단부터 역순으로 읽을 것 (각 항목에 LOG_ID, 목표/발견/수정/검증/
결과가 한국어로 상세히 기록되어 있음).

## 작업 방식 (반드시 이 패턴을 따를 것)

1. **순환 대상**: 댓글/답글, PDS 업로드/다운로드, 회원정보수정, 채팅 4개 영역을 계속 순환한다.
   이미 5~6라운드씩 돈 상태라 얕은 버그는 대부분 소진됐다 — 아래 "다음에 볼 곳" 참고.

2. **탐지 기법 — 이 세션에서 가장 생산적이었던 방법**:
   - `grep -rn "maybeUuid(\|isUuid(" src/server/*.js` 로 UUID 컬럼에 잘못된 값(앱 텍스트 ID)이
     들어가는 자리가 더 있는지 주기적으로 재확인. `context.userId`(앱 자체 텍스트)와
     `context.authUserId`(진짜 Supabase Auth UUID)를 혼동하는 자리가 있으면 100% 버그다.
   - `supabase/migrations/*.sql`에서 테이블 스키마(특히 FK, UNIQUE 제약)를 읽고, 그 컬럼에
     실제로 어떤 값이 쓰이는지 서버 코드와 대조 — 선언된 제약과 실제 코드가 다른 값을 쓰는
     지점을 찾는다(이번 세션 최대 버그 클래스).
   - 클라이언트가 `searchParams`/`payload`에 값을 세팅하는 지점과, 그 값이 실제로 URL/API
     요청에 실리는지, 서버가 그 쿼리스트링을 실제로 읽는지, 리포지토리가 그 값을 필터에
     반영하는지 — 이 체인 전체를 한 번씩 끝까지 추적해볼 것(K 검색 버그가 정확히 이 패턴).
   - "화면엔 성공/적용된 것처럼 보이는데 실제 데이터/요청은 그대로인" 패턴을 의심할 것.

3. **검증**: 이 환경은 네트워크 정책상 실제 외부 Supabase Auth(JWT 로그인)나 raw Postgres
   접속(psql/pg)은 안 될 수 있다(REST API는 프록시를 통과해 정상 작동). `.env`의
   `SUPABASE_SERVICE_ROLE_KEY`로 `@supabase/supabase-js` 클라이언트를 직접 만들어 실제 DB를
   읽고/쓰고 검증하는 방식이 유효했다(이미 여러 라운드에서 이렇게 검증함). 브라우저 테스트가
   필요하면 `public/js/app.js`에 `window.__debugState = state;`를 `const refs = {};` 앞에
   임시로 추가해 Playwright로 `window.__debugState.user = {...}`처럼 로그인 상태를 흉내내고,
   **테스트 끝나면 반드시 `git checkout -- public/js/app.js`로 완전히 되돌릴 것**(커밋에
   포함되면 안 됨).

4. **회귀 테스트**: 수정할 때마다 반드시 관련 스모크(`npm run smoke:boards`,
   `smoke:auth-bridge`, `smoke:chat-rooms` 등 해당 영역) + `node scripts/smoke-command-parity.js`
   + `npm run smoke:full-traversal` + `node scripts/smoke-mobile-viewports.js`를 전부 통과시킬 것.
   후자 둘은 오래 걸리니 백그라운드로 돌리고 완료를 기다릴 것(폴링 대신 알림 대기).

5. **테스트 데이터 정리**: 실제 Supabase(로컬 서버가 실제 운영 DB에 붙는다)에 테스트로 만든
   게시글/첨부파일/대화방/회원을 반드시 정리할 것. 게시글은 DELETE API로, 그 API 경로가 막힌
   고아 데이터는 서비스 롤 키로 직접 삭제. 삭제 전 FK 관계를 스키마로 먼저 확인해 무관한 데이터를
   건드리지 않도록 주의.

6. **커밋 규칙**: 수정 후 `WORK_LOG.md` 최상단에 `## [YYYY-MM-DD HH:MM] [태그] 제목` +
   `**LOG_ID: YYYYMMDD_HHMM**` + 목표/발견/수정/검증/결과 섹션(한국어)을 추가 → 커밋 →
   `claude/12-number-question-41oc5b`에 푸시 → `main`으로 fast-forward 병합 → main 푸시 →
   다시 feature 브랜치로 checkout. 커밋 메시지는 한국어로, "왜"에 초점.

## 다음에 볼 곳 (제안, 강제 아님)
- 회원정보수정: 5~6라운드째 새 버그가 안 나옴 — 이제 다른 영역에 시간을 더 쓰는 게 나을 수 있음.
- 채팅: 메시지 자체가 서버 프로세스 메모리에만 있다는 것(DB 미영속)은 **이미 의도된 설계로
  확인됨** — 재조사 불필요. 대신 `/EX`(수신거부), `/IN`(초대), `/OUT`(강퇴) 명령의 클라이언트-
  서버 값 전달 체인을 K 검색 버그와 같은 방식으로 끝까지 추적해보지 않았음.
- PDS: 첨부파일 다중 업로드 시 일부 실패/일부 성공 케이스의 서버측 트랜잭션 원자성(부분 실패 시
  이미 성공한 파일들이 남는지) 미점검.
- 댓글/답글: 검색(LT/LC/LA)의 다중 게시판 병합(PDS류) 상황에서의 정확성 미점검.
- `supabase/migrations/0021_members_unique_nickname_email.sql`이 실제 DB에 적용됐는지 여부
  확인 — 안 됐다면 psql 접속 가능성 재시도 후 적용 검토(단, 스키마 변경은 파괴적일 수 있으니
  신중히, 필요시 사용자에게 먼저 확인).
