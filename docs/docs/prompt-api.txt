
  너는 시니어 Node.js + Supabase 엔지니어다. 지금부터 기존 작업을 이어받아 `www-bbs` 프로젝트를 분석하고, 실제로 다음 구
  현 방향을 제안하거나 코드를 작성해야 한다.

  프로젝트 개요
  - 프로젝트명: `www-bbs`
  - 목적: 예전 `olddos-bbs-main` BBS를 웹 기반 서비스로 재구현하는 것
  - 현재 환경:
    - OS: Windows
    - Shell: PowerShell
    - 작업 경로: `d:\work\bbs\www-bbs`
    - Node 기반 서버
  - 중요: 로컬 PostgreSQL 설치를 전제로 답하지 말 것. 이미 클라우드 Supabase 프로젝트를 사용 중이다.
  - 중요: 민감정보는 이미 로컬 `.env`에 설정되어 있을 수 있으니, 키 값을 다시 출력하거나 로그에 노출하지 말 것.
  - 중요: 현재 사용자는 “왜 화면이 안 뜨는지”, “어디까지 완성되었는지”, “Supabase를 실제로 쓰는지”에 민감하다. 따라서 현
  재 상태를 코드 기준으로 정확히 설명해야 한다.

  현재 구현 상태 요약
  1. 서버는 이미 동작한다.
  2. `http://localhost:5080/`에 접속하면 JSON만 나온다.
  3. 이것은 오류가 아니라, 아직 프론트엔드 UI가 없고 HTTP API 스캐폴드만 만들어진 상태이기 때문이다.
  4. 게시판 API는 존재한다.
  5. 메모리 저장소와 Supabase 저장소를 분리하는 구조가 들어가 있다.
  6. Supabase 전환용 환경 로더, readiness 체크 스크립트, 마이그레이션 SQL 초안이 있다.
  7. `@supabase/supabase-js`는 설치되어 있다.
  8. `.env`에는 `BOARD_REPOSITORY_DRIVER=supabase` 및 SUPABASE 관련 값이 들어간 상태로 작업 중이다.
  9. 다만 Supabase 쪽이 실제로 완전히 사용 가능한지는 테이블/함수/RPC/데이터 존재 여부를 더 검증해야 한다.
  10. 현재 사용자는 “Supabase는 이미 클라우드에 있는데 왜 로컬 postgres 설치 얘기가 나오느냐”는 문제의식을 갖고 있다. 따
  라서 답변은 Supabase 클라우드 중심으로 해야 한다.

  4. 지금 가장 먼저 해야 할 일은 무엇인가?

  너에게 원하는 작업
  1. 위 파일들을 기준으로 현재 상태를 정확히 진단하라.
  2. “이미 구현된 것 / 아직 미구현인 것 / 위험한 부분 / 착각하기 쉬운 부분”을 분리해서 설명하라.
  3. 특히 `http://localhost:5080/`가 JSON만 반환하는 이유를 사용자가 이해하기 쉽게 설명하라.

  5. Supabase 마이그레이션과 RPC/트리거 설계가 현재 코드와 맞는지 검토하라.
  6. 만약 바로 다음 작업을 해야 한다면 우선순위를 정해서 제안하라.
  7. 가능하면 “프론트엔드 최소 UI 붙이기”와 “Supabase 검증/인증 연결 마무리” 중 무엇을 먼저 해야 하는지 근거와 함께 판단

› supabase를 사용할건데 저렇게 많은 api end point가 필요해?


• 아니요. Supabase를 쓴다 = API endpoint가 많이 필요하다는 뜻은 아닙니다.

  지금 있는 엔드포인트가 많은 이유는 Supabase 때문이 아니라, 현재 프로젝트가 /d:/work/bbs/www-bbs/src/server/app.js 기준
  으로 스캐폴드 + 분석용 메타 + 게시판 도메인 API를 한 서버에 같이 넣어놨기 때문입니다. 그래서 실제 운영용으로 꼭 필요한
  것과, 지금만 필요한 것이 섞여 있습니다.

  핵심

  - 꼭 필요한 것: 게시판 목록, 글 목록, 글 읽기, 글 쓰기, 글 수정, 글 삭제, 추천
  - 상황에 따라 필요한 것: 메뉴 트리/메뉴 resolve
  - 지금은 개발용에 가까운 것: /, /api/meta, /api/boards/meta, /api/boards/contracts, /api/schema/plan, /api/auth/
    meta, /health

  즉, 현재 엔드포인트 수가 많아 보이는 건 자연스럽지만, 운영 기준 최소 세트로 줄이면 훨씬 적어집니다.

  Supabase를 쓸 때 선택지는 2개

  1. 프론트가 Supabase를 직접 호출

  - 서버 API를 많이 줄일 수 있습니다.
  - 대신 권한, 추천 중복 방지, 답글 정렬, 레거시 BBS 규칙을 프론트/RLS/RPC에 많이 넣어야 합니다.
  - 단순 CRUD 앱이면 이 방식이 가볍습니다.

  2. 프론트는 네 서버만 호출, 서버가 Supabase를 사용

  - 지금 구조가 이 방향입니다.
  - 장점: 레거시 규칙을 /d:/work/bbs/www-bbs/src/boards/board-service.js, /d:/work/bbs/www-bbs/src/boards/board-
    repository.js에 모아둘 수 있습니다.
  - 단점: 엔드포인트가 조금 더 많아집니다.
  - 하지만 BBS처럼 규칙이 많은 도메인에는 이쪽이 더 안정적입니다.

  이 프로젝트에서는
  Supabase를 쓰더라도 커스텀 API는 남기는 게 맞습니다.
  이유는 이미 답글 순서(family/orderby/step), 추천 중복 방지, 작성 권한 같은 규칙이 있어서 단순 테이블 CRUD가 아니기 때
  문입니다.

  대신 줄일 수는 있습니다
  운영용 공개 API는 이 정도면 충분합니다.

  - GET /api/boards
  - GET /api/boards/:boardKey/posts
  - GET /api/boards/:boardKey/posts/:no
  - POST /api/boards/:boardKey/posts
  - PATCH /api/boards/:boardKey/posts/:no
  - DELETE /api/boards/:boardKey/posts/:no
  - POST /api/boards/:boardKey/posts/:no/recommend
  - 필요하면 GET /api/menus/tree 또는 GET /api/menus/resolve

  그리고 아래는 내부/개발용으로만 두거나 나중에 빼도 됩니다.

  - /
  - /health
  - /api/meta
  - /api/auth/meta
  - /api/boards/meta
  - /api/boards/contracts
  - /api/schema/plan

  내 판단

  - “저렇게 많은 API가 최종적으로 다 필요하냐?” → 아니요
  - “Supabase를 써도 게시판용 API가 아예 없어도 되냐?” → 그것도 아니요
  - 현재 프로젝트는 게시판 핵심 API 몇 개 + 나머지 메타 API 정리 방향이 맞습니다

  원하면 다음 턴에서 제가 바로

  1. 운영용 endpoint만 남기는 정리안을 만들거나
  2. 현재 endpoint를 public/internal로 분리해서 코드까지 정리하겠습니다.
