작성일: 2026-04-07
최종 검토: 2026-04-07 (코드 기반 전수 검증 완료)

문서 목적
- 이 문서는 data migration 계획서가 아니라, Supabase가 실제로 www-bbs를 운영할 수 있도록 무엇을 먼저 준비해야 하는지 정리한 운영 스키마 준비 문서다.
- 즉 "옛 데이터를 어떻게 옮길까"보다 "회원가입, 게시판, 첨부, 채팅이 지금 코드 기준으로 돌려면 Supabase에 무엇이 있어야 하는가"에 집중한다.
- `retrohello.sql`, `20260407_retrohello_DB_Backup.sql`, `legacy/hanulso.mnu`는 참고 소스이고, 최종 기준은 현재 repo의 서버 코드와 라우터다.

[기존 migration 파일 현황 — 검증 완료]

supabase/migrations/ 폴더에 이미 존재하는 파일 목록과 실제 처리 내용:

  0001_initial_schema.sql
    → members, boards, posts, attachments, post_recommendations, memos 초기 생성 정의를 담고 있다
    → 다만 현재 live Supabase 프로젝트에는 boards, post_recommendations가 실제로 없고, posts도 0001의 legacy 컬럼 셋이 그대로 반영되어 있지 않다

  0002_attachment_storage_columns.sql
    → attachments에 nick_name, mime_type, content_base64 추가 (완결)

  0003_memo_schema_alignment.sql
    → memos 컬럼 정렬 (sender_user_id, recipient_user_id 등 정비, 완결)

  0004_members_table_bootstrap.sql
    → members 테이블 pgcrypto 확장 활성화 + nick_name/email 인덱스 보강
    → auth_user_id, updated_at은 여기서도 미추가 → 0009에서 추가 예정

  0005_members_attachments_rls.sql
    → members, attachments에 RLS 활성화
    → 서버는 service_role로 RLS 우회. 브라우저가 public 테이블에 직접 접근하는 구조는 사용하지 않음 (설계 원칙과 일치)

  0006_security_hardening.sql
    → Supabase 내부 보안 함수 설정 (특별한 테이블 작업 없음)

  0007_chat_room_repository_alignment.sql
    → ⚠️ 버그: chat_rooms가 존재한다고 가정하고 ALTER만 실행
    → 신규 Supabase 프로젝트에 0001~0008을 순서대로 적용하면 0007에서 실패
    → 해결: 0007을 직접 수정하여 CREATE TABLE IF NOT EXISTS → ALTER TABLE 순으로 재작성
    → chat_room_members도 동일하게 CREATE IF NOT EXISTS 추가 필요

  0008_rss_cache.sql
    → rss_cache 테이블 + expires_at 인덱스 생성 (완결)
    → 추가 migration 불필요

[2026-04-07 live 검증 결과]

- `public.members`: 존재. 하지만 `auth_user_id`, `updated_at` 없음
- `public.boards`: 없음. 현재 `/api/boards`는 메뉴 fallback으로만 동작
- `public.posts`: 존재. 현재 live 컬럼은 `author_id`, `author_nickname`, `hits`, `is_notice`, `is_hidden` 쪽이고, 계층형 답글용 `family_id`, `sort_order`, `depth`와 추천수 `recommend`는 없음
- `public.post_recommendations`: 없음
- `public.attachments`: 존재. `content_base64`까지 있음. `storage_bucket`, `storage_path`만 없음
- `public.memos`: 존재. 현재 코드 기대 범위 충족
- `public.chat_rooms`, `public.chat_room_members`, `public.rss_cache`: 존재하고 live probe 통과

중요 결론
- repo에 migration 파일이 존재한다는 사실과, 현재 Supabase 프로젝트에 그 스키마가 실제 반영되어 있다는 사실은 다르다.
- 따라서 `0010_boards_runtime_alignment.sql`, `0011_posts_runtime_alignment.sql`, `0012_post_recommendations_alignment.sql`은 "보강"만이 아니라 "CREATE TABLE IF NOT EXISTS를 포함한 bootstrap-safe migration"이어야 한다.


0. Supabase 전역 준비

반드시 준비
- Supabase Auth Email provider 사용 여부 결정
- 브라우저용 `anon/publishable key`
- 서버용 `service_role key`
- `pgcrypto` extension (0004에서 이미 처리됨)
- `public` 스키마 테이블 생성 권한과 migration 실행 경로

RLS 주의사항
- 0005가 members, attachments에 RLS를 켰다.
- 서버는 service_role로 RLS를 우회하므로 문제없다.
- RLS 정책(Policy)을 별도로 추가하지 않으면 anon key 직접 쿼리 시 빈 결과가 반환된다.
- 현재 설계(브라우저가 public 테이블에 직접 접근하지 않음)와 일치하므로 v1에서는 그대로 유지한다.

현재 코드 기준 중요한 운영 결정
- `auth.users`는 브라우저에서 직접 `signUp()` 한다.
- `public.*` 테이블은 서버가 `service_role`로 읽고 쓴다.
- 즉 브라우저가 `members`, `posts`, `attachments` 같은 `public` 테이블에 직접 쓰는 구조는 아니다.
- 따라서 v1에서는 public 테이블 RLS를 공격적으로 복잡하게 설계하기보다, 서버 전용 쓰기 구조를 유지하는 편이 안전하다.

가장 중요한 주의
- 현재 프런트 가입 흐름은 `supabase.auth.signUp()` 후 `session.access_token`이 바로 있을 때만 `/api/members/profile`로 `public.members` 프로필을 생성/보정한다.
- 그래서 Email Confirm를 켜면 가입 직후 세션이 없을 수 있고, 그 경우 `public.members` 동기화가 누락될 수 있다.
- v1 선택지는 둘 중 하나다.
- 선택지 A: Email Confirm를 끄고, 가입 직후 세션이 생기게 한다.
- 선택지 B: Email Confirm를 켜되, 이메일 인증 뒤 첫 로그인 시 `members` 프로필을 강제 생성하는 후속 로직을 추가한다.
- 현재 코드만 기준으로는 선택지 A가 더 안전하다.

2. 기능별 Supabase 준비 명세

2-1. 회원가입 / 로그인 / 프로필

Supabase가 준비할 것
- `auth.users`
- `public.members`

현재 코드 흐름
- 브라우저: `supabase.auth.signUp(email, password, { data: { userId, nickname } })`
- 브라우저: 성공 직후 세션이 있으면 `/api/members/profile` 호출
- 서버: `AuthBridge`가 Bearer token으로 `auth.users` 세션 확인
  - `user_metadata.userId` → 커스텀 userId
  - `user_metadata.nickname` 또는 `user_metadata.nick_name` → 닉네임
- 서버: `MemberRepositorySupabase`가 `public.members` 읽기/쓰기
  - 기본 테이블명: `members` (환경변수 `SUPABASE_MEMBERS_TABLE`로 변경 가능)
  - upsert 기준: `user_id` (onConflict)

`public.members` 필수 컬럼
- `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`
- `auth_user_id UUID UNIQUE NULL REFERENCES auth.users(id) ON DELETE SET NULL`  ← 0009에서 추가
- `user_id TEXT NOT NULL`
- `nick_name TEXT NOT NULL`
- `email TEXT NULL`
- `password TEXT NOT NULL DEFAULT ''`
- `birthday TEXT NOT NULL DEFAULT ''`
- `sex TEXT NOT NULL DEFAULT 'M'`
- `level INT NOT NULL DEFAULT 1`
- `is_open BOOLEAN NOT NULL DEFAULT true`
- `is_admin BOOLEAN NOT NULL DEFAULT false`
- `registration_datetime TIMESTAMPTZ NOT NULL DEFAULT now()`
- `lastlogin_datetime TIMESTAMPTZ NOT NULL DEFAULT now()`
- `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`
- `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`  ← 0009에서 추가

필수 제약 / 인덱스
- `UNIQUE(user_id)`
- `UNIQUE(nick_name)`
- `UNIQUE(email) WHERE email IS NOT NULL` (조건부 unique index) ← 0009에서 추가
- `INDEX(auth_user_id)` ← 0009에서 추가
- `INDEX(level)` ← 0009에서 추가

운영 메모
- `password`는 장기적으로 제거 대상이지만, 현재 `MemberRepositorySupabase.js`가 직접 사용하므로 v1에서는 유지해야 한다.
- `auth_user_id`는 반드시 추가해야 하는 브리지 컬럼이다. 0001/0004에 없으므로 0009에서 추가한다.
- 닉네임과 이메일은 현재 서버 코드가 중복 검사를 한다. DB에서도 unique로 막아야 한다.

회원가입에서 Supabase가 준비해야 하는 것
- Email auth 활성화
- 회원가입 허용 여부 결정
- Email Confirm ON/OFF 결정
- `public.members` 생성 (0001에서 완료, 0009에서 보강)
- `auth_user_id`, `user_id`, `nick_name`, `email` unique 제약 준비
- 서버가 `service_role`로 `members` upsert 가능해야 함

2-3. 게시글 / 답글

Supabase가 준비할 것
- `public.posts`

현재 코드 흐름
- `/api/boards/:boardId`
- `/api/boards/:boardId/posts`
- `/api/boards/:boardId/posts/:postId`
- `/api/boards/:boardId/posts/:postId/reply`
- 기본 테이블명: `posts` (환경변수 `SUPABASE_POSTS_TABLE`로 변경 가능)
- 현재 repository가 계층형 답글 여부를 판단할 때 실제로 보는 컬럼은 `family_id`, `sort_order`, `depth`다.
- 현재 row reader는 `author_id/user_id`, `author_nickname/nick_name`, `hits/hit`처럼 일부 fallback을 허용한다.
- 하지만 live 프로젝트에는 `family_id`, `sort_order`, `depth`, `recommend`가 없어서, 목록/본문은 읽혀도 classic BBS식 답글 계층과 추천 기능은 스키마 차원에서 완성되지 않았다.
- 문서 초안에서 적어둔 `SUPABASE_FAMILY_COLUMN`, `SUPABASE_ORDER_COLUMN`, `SUPABASE_STEP_COLUMN` 방식은 현재 `createBoardRepositoryFromEnv()`에 실제로 연결되어 있지 않다.
- 따라서 v1 운영 스키마 기준으로는 DB에 `family_id`, `sort_order`, `depth`를 직접 준비하는 편이 안전하다.

`public.posts` 필수 컬럼
- `id BIGSERIAL PRIMARY KEY`
- `board_id TEXT NOT NULL REFERENCES public.boards(board_id) ON DELETE CASCADE`
- `author_id UUID NULL REFERENCES auth.users(id) ON DELETE SET NULL`  ← 0011에서 추가
- `author_nickname TEXT NOT NULL DEFAULT ''`
- `user_id TEXT NOT NULL DEFAULT 'guest'`        ← 권장 compatibility 컬럼
- `nick_name TEXT NOT NULL DEFAULT ''`           ← 권장 compatibility 컬럼
- `family_id BIGINT NOT NULL DEFAULT 0`          ← 0011에서 추가/보장
- `sort_order BIGINT NOT NULL DEFAULT 0`         ← 0011에서 추가/보장
- `depth INT NOT NULL DEFAULT 0`                 ← 0011에서 추가/보장
- `title TEXT NOT NULL DEFAULT ''`
- `content TEXT NOT NULL DEFAULT ''`
- `hits INT NOT NULL DEFAULT 0` 또는 `hit INT NOT NULL DEFAULT 0`  ← 둘 중 하나는 반드시 있어야 함. live 현재는 `hits`
- `recommend INT NOT NULL DEFAULT 0`             ← 0011에서 추가/보장
- `is_notice BOOLEAN NOT NULL DEFAULT false`   ← 0011에서 추가
- `is_hidden BOOLEAN NOT NULL DEFAULT false`   ← 0011에서 추가
- `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`
- `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`

필수 제약 / 인덱스
- `INDEX(board_id)` ← 0001에 존재
- `INDEX(board_id, family_id, sort_order)` ← 0011에서 추가/보장
- `INDEX(board_id, created_at DESC)` ← 0011에서 추가
- `INDEX(author_id)` ← 0011에서 추가

운영 메모
- `author_id`는 Auth 사용자와의 정합성용이다.
- `author_nickname`는 현재 live 프로젝트가 실제로 쓰는 작성자 표시 컬럼이다.
- `user_id`, `nick_name`은 guest 글쓰기와 레거시/import 호환성을 위해 같이 두는 편이 좋다.
- 답글 정렬 때문에 `family_id/sort_order/depth`는 절대 빠지면 안 된다.
- 기존 0001 스타일 `family/orderby/step`은 import용 보조 컬럼로는 의미가 있지만, 현재 runtime이 직접 보는 기준은 아니다.

게시글에서 Supabase가 준비해야 하는 것
- `posts` 테이블 생성 또는 보장 (`0011`이 `CREATE TABLE IF NOT EXISTS`까지 포함해야 함)
- 게시판 FK 연결
- 답글 계층 정렬 컬럼 준비 (`family_id`, `sort_order`, `depth`)
- 조회수/추천수 누적 컬럼 준비 (`hits` 또는 `hit`, 그리고 `recommend`)


2-4. 추천

- `user_id TEXT NOT NULL`
- `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`

필수 제약 / 인덱스
- `UNIQUE(post_id, user_id)` ← 0001에 존재
- `INDEX(user_id)`

추천에서 Supabase가 준비해야 하는 것
- 추천 이력 테이블 생성 보장 (`0012`가 `CREATE TABLE IF NOT EXISTS`까지 포함해야 함)
- 중복 추천 방지 unique 제약 준비
- `INDEX(user_id)` 보강


2-5. 첨부파일

Supabase가 준비할 것
- `public.attachments`

현재 코드 흐름
- 첨부는 아직 Supabase Storage가 아니라 DB `content_base64`를 직접 읽는다.
- 즉 v1에서 다운로드가 되려면 object storage만으로는 부족하고, `content_base64`가 필요하다.

4. 1차 Supabase migration 작업 단위

작업 0. 0007 migration 수정 (신규 프로젝트 bootstrap 가능하게)
- 문제:
  0007_chat_room_repository_alignment.sql이 chat_rooms를 CREATE하지 않고 ALTER만 실행해서 신규 프로젝트에서 실패.
- 해결:
  0007을 직접 수정한다.
  - CREATE TABLE IF NOT EXISTS public.chat_rooms (전체 컬럼 포함)
  - CREATE TABLE IF NOT EXISTS public.chat_room_members (전체 컬럼 포함)
  - 기존 ALTER TABLE ... ADD COLUMN IF NOT EXISTS 유지 (이미 배포된 프로젝트와 호환)
- 완료 기준:
  빈 Supabase 프로젝트에서 0001~0008을 순서대로 실행했을 때 오류 없이 완료됨.

작업 1. 회원/인증 레이어 정리
- 목표 기능:
  회원가입, 로그인, `/api/members/search`, `/api/members/profile`, `/api/members/register`
- 권장 migration 파일:
  `0009_members_runtime_alignment.sql`
- 이 migration에서 할 일:
  - members에 auth_user_id UUID UNIQUE NULL REFERENCES auth.users(id) ON DELETE SET NULL 추가
  - members에 updated_at TIMESTAMPTZ NOT NULL DEFAULT now() 추가
  - email 조건부 unique index 생성: WHERE email IS NOT NULL
  - auth_user_id 인덱스 생성
  - level 인덱스 생성
- 배경:
  0001과 0004 모두 auth_user_id와 updated_at이 없음. 이 migration에서 최초로 추가.
- 완료 기준:
  signup 후 auth.users와 public.members가 함께 정리되고, 닉네임/이메일 중복이 DB 레벨에서도 막힌다.

작업 2. 게시판 메타데이터 정리
- 목표 기능:
  `/api/boards`, `/api/boards/:boardId`
- 권장 migration 파일:
  `0010_boards_runtime_alignment.sql`
- 이 migration에서 할 일:
  - boards를 `CREATE TABLE IF NOT EXISTS`로 bootstrap
  - boards에 base 컬럼(name/menu_path/door/access_level/write_sysop_only/reply_enabled/attachment_enabled/header_file/footer_file/created_at) 보장
  - boards에 group_key TEXT NOT NULL DEFAULT 'top' 추가
  - boards에 sort_order INT NOT NULL DEFAULT 0 추가
  - boards에 is_active BOOLEAN NOT NULL DEFAULT true 추가
  - boards에 updated_at TIMESTAMPTZ NOT NULL DEFAULT now() 추가
  - UNIQUE(board_id) 보장
  - INDEX(menu_path, sort_order), INDEX(group_key, sort_order) 추가
  - 2-2절 board seed 목록 전체를 upsert로 입력
- 중요한 결정:
  canonical board_id를 legacy/hanulso.mnu 기준으로 고정한다.
  board_id 목록: notice, tosysop, plaza, humor, say, qna, newface, locnews, entertain,
                 carpool, mystery, novice, pds_all, pds_util, pds_game, pds_graphic,
                 pds_sound, pds_prog
- 완료 기준:
  live 프로젝트에서 메뉴 fallback이 아니라 실제 `public.boards`가 `/api/boards`의 소스가 된다.

작업 3. 게시글/답글/추천 레이어 정리
- 목표 기능:
  목록, 본문, 작성, 수정, 삭제, 답글, 추천
- 권장 migration 파일:

  - posts에 `recommend` 추가
  - posts에 author_id UUID NULL REFERENCES auth.users(id) ON DELETE SET NULL 추가

  - posts에 is_notice BOOLEAN NOT NULL DEFAULT false 추가

5. 실제 구현 진행 순서

권장 방식
- 백엔드 계약을 먼저 고정하고, 기능별로 프론트와 연결한다.
- 즉 전체 백엔드를 다 만든 뒤 프론트를 붙이는 방식이 아니라, 기능 단위 세로 슬라이스로 진행한다.

실제 순서
- 1) 작업 0:
  0007을 idempotent하게 수정하여 신규 프로젝트에서 0001~0008 전체가 오류 없이 실행되게 한다.
- 2) 작업 1:
  회원가입/로그인에 필요한 Auth 정책과 members를 먼저 고정한다.
- 3) 작업 2~3:
  boards, posts, post_recommendations를 맞춰서 게시판 읽기/쓰기 슬라이스를 완성한다.
- 4) 작업 4:
  첨부를 붙여 게시판 한 세트를 완성한다.
- 5) 작업 5:
  쪽지를 붙인다.
- 6) 작업 6:
  채팅을 검증한다 (작업 0 완료 후 바로 동작 가능).
- 7) 작업 7:
  RSS 캐시 0008 동작 확인 (추가 작업 없음).
- 8) 작업 8:
  마지막으로 메뉴/설정/정적 페이지를 DB-backed router 구조로 옮긴다.

기능 슬라이스 기준 검증 순서
- 슬라이스 1:
  회원가입 -> 로그인 -> 프로필 조회/수정
- 슬라이스 2:
  게시판 목록 -> 글 목록 -> 본문 -> 글쓰기 -> 답글 -> 추천
- 슬라이스 3:
  첨부 업로드 -> 다운로드 -> 삭제
- 슬라이스 4:
  쪽지 작성 -> 목록 -> 읽음 -> 삭제
- 슬라이스 5:
  채팅방 생성 -> 입장 -> 퇴장 -> 목록 반영
- 슬라이스 6:
  메뉴/설정/정적 페이지 DB 전환

7. 최종 결론

- 이 문서는 migration 범위 문서가 아니라 "Supabase가 실제로 준비해야 하는 운영 스키마 명세"로 읽혀야 한다.
- 가입은 `auth.users + public.members` 두 층이 필요하고, Email Confirm 정책까지 같이 결정해야 한다.
- 게시판은 `boards + posts + post_recommendations + attachments`를 한 세트로 준비해야 한다.
- 채팅은 `chat_rooms + chat_room_members`, 쪽지는 `memos`, RSS는 `rss_cache`가 각각 독립 기능 단위다.
- router를 DB로 옮길 준비까지 하려면 2차로 `menu_nodes`, `site_config`, `content_pages`, `board_groups`가 필요하다.
- 0001~0008은 이미 존재하며, 0007 수정 + 0009~0015 추가로 v1 운영 준비가 완성된다.
- 기존 migration 0002/0003/0008이 이미 처리한 작업(attachments content_base64, memos 컬럼, rss_cache)은 중복 실행하지 않는다.
